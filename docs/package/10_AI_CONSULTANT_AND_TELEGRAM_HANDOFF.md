# AI Consultant and Telegram Lead Handoff — Core Requirement

This document contains two must-have behaviors. Do not reduce them to a generic chatbot or a Telegram share link.

## A. The advisor solves the business problem
The customer may not know which NFC object or digital flow to ask for. The AI consultant is responsible for discovering the problem and helping them imagine a better solution.

### Consultant conversation loop
1. Listen and reflect the customer context briefly; don't dump a long questionnaire.
2. Identify goal/friction, audience, setting/placement and desired action. Ask one high-value clarifier if a key detail is missing.
3. Offer at least two or three distinct and contextually useful ideas when enough context exists. Explain trade-offs simply.
4. Recommend a best-fit direction, explicitly stating why. The customer can choose another direction or ask for adjustment.
5. Compose a personalized offer with the proposed physical object, digital experience after tap/scan, design direction, included components, why it fits, what is confirmed, what needs human confirmation, price type and a clear next step.
6. Save this in the canonical record and only then build the concept visualization.

### Knowledge and quality strategy
- A curated source of truth should describe all current products, available colors/materials/shapes/dimensions, pricing rules, compatible destinations, digital capabilities, actual case features, production limits and escalation rules.
- Use model prompting + retrieval/structured tools + runtime schema validation; tool-backed pricing and product IDs; multilingual examples; automated evaluations.
- Do not train a custom model at launch. “Good consultant” quality depends on data, reasoning instructions, interaction design and evaluation—not just model size.
- The system should be tested for recommendation relevance, originality, fact fidelity, language naturalness, number of turns to useful offer, correct abstention, schema compliance and safe escalation.

## B. Canonical JSON contract
The advisor output is parsed, validated and normalized by server-side code. Image generation, pricing, offer UI and Telegram must consume the same accepted record. The exact schema lives in `03_AI_CONCEPT_STUDIO.md`; no downstream layer should infer different product properties from a free-form paragraph.

Canonical fields include language, lead/concept ID, business/goal context, recommendation, physical product type, digital experience, selected geometry/color/material/finish/text/logo, QR destination, quantity, offer, validated price source, production feasibility status, image attempt number, preview asset, and handoff status.

Important rules:
- Prices are derived from deterministic business rules.
- QR is generated by code from the actual URL.
- AI-generated product IDs/materials/colors/prices/production feasibility cannot be treated as confirmed facts.
- A generated preview is conceptual and must be visibly labeled as such.

## C. Two-image budget and anti-abuse
- Maximum two successful image generations per design session/visitor. Show remaining count. After that, offer the human team.
- Enforce with persistent server-side state and signed visitor/session identity; never trust a front-end counter or browser-only state.
- Support with per-IP burst throttling (not IP-only lifetime blocking), chat turn/token caps, one active generation job, request idempotency, upload limits, a suspicious-traffic challenge when necessary, daily image output hard cap and daily spend stop.
- Starting defaults are configurable in `.env.example`: 2 images/session, 24 consultant turns, 8 chat requests/minute, 100 image outputs/day, 1 active job/session. Adjust after observed abuse and conversion data, not by removing controls.
- A provider timeout should not create endless free retry attempts. Treat generation status and credit consumption transactionally.

## D. CTA and real image delivery to Telegram
UI CTA: **“Send concept to manager”** or natural localized equivalent. Before click, disclose that the concept image and brief will be shared with the team through Telegram.

On click:
1. Server validates ownership/session and lead record; persist lead and preview first.
2. Server fetches/streams the trusted stored preview (never trust an arbitrary URL from the browser) and uses Telegram Bot API `sendPhoto` to send it to `TELEGRAM_MANAGER_CHAT_ID`.
3. Photo caption or associated message includes a greeting context, personalized offer summary, business goal, recommended product/experience, key design properties, quantity/price type if known, open questions, locale, concept ID and hosted preview link.
4. Use idempotency so retries/double-clicks do not duplicate the same inquiry. Store message ID and delivery timestamp, not the bot token in logs.
5. Confirm “Sent to our team” only after Telegram reports success. Show pending/failure honestly. Keep a copyable summary, preview link and optional direct human Telegram link as fallback.

Sample manager caption structure:
> New Touchform.md concept inquiry · ID: TF-…
> Business: …
> Goal: …
> Recommendation: …
> Physical product/design: …
> Digital experience: …
> Personalized offer: …
> Quantity / pricing: …
> Needs human confirmation: …
> Language: …
> Preview: https://…

The bot must be configured by the project owner: create it manually, add it to a private manager group or target chat, give it posting rights, supply token and numeric chat ID as server environment variables. The agent should implement and test against a mock but must not invent credentials. Live test is blocked until those credentials exist.

## E. Why not only a Telegram URL?
Telegram's official share URL (`https://t.me/share/url?url=...&text=...`) lets the user choose a destination chat and edit text containing a link. It does not pre-attach the generated image as an upload. Bot API `sendPhoto` sends the actual image to a configured chat. This is why the AI-image CTA is a backend/bot action while the ordinary catalog order may remain a prefilled-message link.
